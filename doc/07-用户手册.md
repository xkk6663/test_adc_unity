## 1. 快速开始

### 1.1 环境准备

| 工具 | 最低版本 | 用途 | 安装方式 |
|------|----------|------|----------|
| gcc / clang / MSVC | C99 兼容 | C 编译器 | 系统自带或 MinGW / Visual Studio |
| make | 3.8+ | Makefile 构建 | `sudo apt install make` / MinGW |
| CMake | 3.10+ | CMake 构建 | `sudo apt install cmake` / 官网下载 |
| Ruby | 2.5+ | 重新生成 CMock 桩（可选） | `sudo apt install ruby` / RubyInstaller |

> **注意**：桩文件已检入仓库，**没有 Ruby 也能直接编译运行**。Ruby 仅在修改 HAL 接口后需要重新生成桩时使用。

### 1.2 获取代码

```bash
git clone git@github.com:xkk6663/test_adc_unity.git
cd test_adc_unity
```

### 1.3 编译运行（Makefile 方式）

```bash
# 编译（单元测试 + 固件模拟）
make all

# 运行单元测试
make test
# 预期输出：19 Tests 0 Failures 0 Ignored

# 运行固件模拟
make firmware
```

**Windows（MinGW）**：将 `make` 替换为 `mingw32-make`。

### 1.4 编译运行（CMake 方式）

```bash
# 配置
cmake -S . -B build

# 构建
cmake --build build

# 运行测试（CTest）
cd build
ctest --output-on-failure
```

## 2. 工程结构导航

```
test_adc_unity/
├── app/              # 业务模块（你写的代码）
│   ├── battery/      # 电池电压采集
│   └── led/          # LED 指示灯
├── hal/              # 硬件接口（你定义的契约）
├── platform/         # 固件主程序（真实 HAL 实现）
├── test/             # 测试代码
│   ├── unit/         # 单元测试用例
│   └── mocks/        # CMock 自动桩
├── framework/        # Unity + CMock（第三方，不用改）
├── tools/            # 桩生成脚本
├── doc/              # 全套产品开发文档
└── .github/          # CI/CD 配置
```

**你通常只需要关心**：
- 写业务代码 → `app/`
- 定义硬件接口 → `hal/`
- 写测试用例 → `test/unit/`
- 看文档 → `doc/`

## 3. 常见操作指南

### 3.1 如何新增一个业务模块

以新增 `sensor` 模块为例：

**第 1 步：创建模块目录和文件**
```bash
mkdir app/sensor
# 创建 app/sensor/sensor.h 和 app/sensor/sensor.c
```

**第 2 步：如需新硬件接口，在 hal/ 中添加**
```bash
# 创建 hal/hal_sensor.h，声明 HAL_SENSOR_Read() 等函数
```

**第 3 步：生成 CMock 桩**
```bash
# 编辑 tools/gen_mocks.rb，在 header_files 中添加 'hal/hal_sensor.h'
ruby tools/gen_mocks.rb
```

**第 4 步：编写测试用例**
```bash
# 创建 test/unit/test_sensor.c
```

**第 5 步：注册到测试框架**
- 在 `test/unit/test_support.c` 中添加 extern 声明
- 在 `main()` 中添加 `RUN_TEST(test_sensor_xxx)`
- 在 `setUp()/tearDown()` 中添加桩的 Init/Verify/Destroy

**第 6 步：更新构建系统**
- Makefile：在 `TEST_SRCS` 中添加新文件
- CMakeLists.txt：在 `unit_test` 目标中添加新文件

**第 7 步：验证**
```bash
make all && ./unit_test    # 本地验证
git push                   # CI 自动验证
```

### 3.2 如何修改 HAL 接口

1. 修改 `hal/hal_xxx.h` 中的函数原型
2. 重新生成桩：`ruby tools/gen_mocks.rb`
3. 更新所有调用该接口的业务代码
4. 更新测试用例中的 Expect 调用
5. 运行 `make test` 验证

### 3.3 如何查看测试覆盖率

CI 会自动生成覆盖率报告。本地生成：

```bash
# 需要安装 lcov
make clean
make all CFLAGS="-Wall -Wextra -std=c99 --coverage -O0 -g"
./unit_test
lcov --capture --directory . --output-file coverage.info
genhtml coverage.info --output-directory coverage-report
# 打开 coverage-report/index.html 查看
```

### 3.4 如何运行静态分析

```bash
# 需要安装 cppcheck
cppcheck --enable=warning,style,performance,portability \
         -I app/battery -I app/led -I hal \
         app/ hal/ platform/
```

## 4. 测试用例编写指南

### 4.1 基本套路

每个测试用例遵循四步：

```c
void test_xxx(void)
{
    // 1. 预设外部依赖（CMock 桩）
    HAL_ADC_GetValue_ExpectAndReturn(2048);

    // 2. 调用被测函数
    uint16_t result = read_battery_mv();

    // 3. 断言结果
    TEST_ASSERT_EQUAL_UINT16(1650, result);

    // 4. tearDown 自动校验桩调用（不用写）
}
```

### 4.2 常用断言宏

| 宏 | 用途 |
|----|------|
| `TEST_ASSERT_EQUAL_INT(expected, actual)` | 整数相等 |
| `TEST_ASSERT_EQUAL_UINT16(expected, actual)` | uint16 相等 |
| `TEST_ASSERT_TRUE(condition)` | 条件为真 |
| `TEST_ASSERT_NULL(pointer)` | 指针为空 |
| `TEST_ASSERT_EQUAL_INT_ARRAY(exp, act, num)` | 数组相等 |

### 4.3 CMock 桩常用 API

| API | 用途 |
|-----|------|
| `Func_ExpectAndReturn(arg, ret)` | 预设一次调用，校验参数，返回指定值 |
| `Func_IgnoreAndReturn(ret)` | 忽略调用，总是返回指定值 |
| `Func_Expect(arg)` | 预设一次 void 函数调用，校验参数 |
| `Func_Ignore()` | 完全忽略调用 |

## 5. CI/CD 使用指南

### 5.1 触发条件

- push 到 `main` 分支
- 向 `main` 分支发起 Pull Request

### 5.2 查看结果

1. 打开仓库页面 → Actions 标签
2. 点击最新的 workflow run
3. 查看三个 Job 的状态：
   - **Static Analysis**：cppcheck 结果
   - **Build & Test**：三平台构建测试结果
   - **Test Coverage**：覆盖率报告

### 5.3 下载产物

在 workflow run 页面底部的 **Artifacts** 区域：
- `binaries-ubuntu-latest`：Ubuntu 编译的可执行文件
- `binaries-macos-latest`：macOS 编译的可执行文件
- `binaries-windows-latest`：Windows 编译的可执行文件
- `coverage-report`：HTML 覆盖率报告（解压后打开 index.html）

## 6. 故障排查

### 6.1 编译报错

| 错误信息 | 原因 | 解决 |
|----------|------|------|
| `fatal error: unity.h: No such file` | 头文件路径不对 | 检查 Makefile 的 `-Iframework/unity` |
| `fatal error: cmock.h: No such file` | 缺少 CMock C 运行时 | 检查 `-Iframework/cmock/src` 和 cmock.c |
| `undefined reference to mock_hal_adc_Init` | 桩文件未编译 | 检查 TEST_SRCS 是否包含 test/mocks/*.c |
| `./unit_test: No such file or directory` | 可执行文件名不匹配 | Linux 上无 .exe 后缀，检查 Makefile |

### 6.2 测试失败

| 现象 | 原因 | 解决 |
|------|------|------|
| `Function called less times than expected` | 桩期望调用次数多于实际 | 检查被测函数是否真的调用了该 HAL |
| `Function called more times than expected` | 实际调用次数多于期望 | 检查是否有多余的调用，或用 Ignore() |
| `Expected parameter 1 to be ... was ...` | 参数不匹配 | 检查 Expect 中设置的参数是否正确 |
| 测试全部通过但 tearDown 报错 | 桩未正确销毁 | 检查 test_support.c 的 tearDown |

### 6.3 CI 失败

详细的 CI 排错记录见 [CI-CD排错日志.md](../CI-CD排错日志.md)。

常见快速排查：
1. 本地能否复现？→ 能：代码问题；不能：平台差异
2. 哪个 Job 失败？→ static-analysis：代码风格；build-and-test：编译/测试；coverage：覆盖率工具
3. 哪个平台失败？→ 仅 Windows：shell/路径问题；仅 macOS：brew 依赖问题

## 7. 最佳实践

1. **先写测试再写实现**（TDD）：先在 test/unit/ 写用例，再在 app/ 写实现
2. **每次修改后运行 `make test`**：确保不破坏已有功能
3. **提交前本地验证**：`make clean && make all && ./unit_test`
4. **新增模块同步更新文档**：doc/ 下的设计文档和测试用例
5. **CI 失败立即修复**：不要让 main 分支长时间处于红色状态
