> 文档版本：v1.0

---

## 1. 文档目的

本文档定义"嵌入式电池电压监测与指示模块"的市场需求，包括目标市场、用户痛点、竞品分析、商业目标和功能需求边界，作为产品开发（PRD）和技术设计的输入依据。

---

## 2. 目标市场

### 2.1 市场定义

面向**低功耗嵌入式设备**的电池供电场景，包括但不限于：

| 细分市场 | 典型产品 | 电池类型 |
|----------|----------|----------|
| 消费电子 | 无线鼠标、键盘、遥控器 | AA/AAA 碱性电池 |
| 物联网 | 温湿度传感器、智能门锁 | 锂电池（3.7V） |
| 工业控制 | 便携式检测仪、数据采集器 | 镍氢电池组 |
| 可穿戴 | 手环、手表 | 锂聚合物电池 |

### 2.2 市场规模

- 全球嵌入式电池管理 IC 市场 2025 年预计达 **$45 亿**，年复合增长率 8.2%
- 中国市场占比约 35%，中低端 MCU 方案需求旺盛
- 趋势：低成本、低功耗、高集成度是核心竞争点

## 3. 目标用户与痛点

### 3.1 用户画像

| 用户类型 | 角色 | 核心诉求 |
|----------|------|----------|
| 嵌入式工程师 | 产品开发者 | 快速集成、代码可测试、文档完善 |
| 硬件工程师 | 电路设计 | 接口清晰、硬件抽象层稳定 |
| 测试工程师 | 质量保障 | 可自动化测试、覆盖率可度量 |
| 项目经理 | 进度管理 | CI/CD 自动化、交付可预测 |

### 3.2 核心痛点

1. **硬件依赖强**：业务代码与硬件寄存器耦合，无法在 PC 上单元测试
2. **测试成本高**：每次修改都要烧录到硬件验证，迭代周期长
3. **代码质量不可控**：缺乏静态检查和自动化测试，bug 流入硬件测试阶段
4. **跨平台移植难**：换 MCU 平台时业务代码需要大量修改
5. **文档缺失**：开源 Demo 通常只有代码，没有完整的产品开发文档链路

## 4. 竞品分析

### 4.1 竞品对比

| 维度 | 传统裸机开发 | Ceedling 框架 | 本方案（Unity+CMock+ELAB分层） |
|------|-------------|--------------|-------------------------------|
| 单元测试 | 无/手写桩 | Unity+CMock 集成 | Unity+CMock，vendor 到工程 |
| 代码分层 | 扁平结构 | 按模块分目录 | ELAB 风格六层分层 |
| CI/CD | 无 | 需自行配置 | 开箱即用三 Job 流水线 |
| 跨平台 | 差 | 较好 | 好（Windows/Linux/macOS） |
| 学习成本 | 低 | 中（需学 Ceedling） | 中（纯 Makefile/CMake） |
| 文档 | 无 | 英文为主 | 中文完整文档链 |
| 硬件依赖 | 强 | 弱（HAL 抽象） | 弱（HAL 接口 + CMock 桩） |

### 4.2 差异化优势

1. **零额外依赖**：Unity/CMock 源码 vendor 到工程，无需安装 Ceedling/Ruby 环境即可编译
2. **产品级架构**：仿照 ELAB 框架分层，可直接用于真实产品开发
3. **完整文档链**：从 MRD 到运维的全套中文文档
4. **CI/CD 开箱即用**：静态分析 + 多平台矩阵 + 覆盖率，push 即触发
5. **教学友好**：每个模块有详细中文注释，测试用例覆盖典型设计模式

## 5. 商业目标

### 5.1 短期目标（3 个月）

- 成为嵌入式单元测试教学的标准参考工程
- GitHub Star 达到 100+
- 被至少 3 个嵌入式培训课程引用

### 5.2 中期目标（6 个月）

- 扩展到 5+ 典型业务模块（ADC、GPIO、UART、SPI、I2C）
- 支持 FreeRTOS 集成测试
- 发布配套视频教程

### 5.3 长期目标（12 个月）

- 形成嵌入式产品开发最佳实践模板
- 支持自动生成模块脚手架（新增模块一键生成代码+测试+CI）
- 建立社区贡献机制

## 6. 功能需求边界

### 6.1 必须包含（MVP）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-001 | 电池电压采集模块（ADC 采样 + 电压换算） | P0 |
| F-002 | LED 指示灯模块（根据电压显示红/绿状态） | P0 |
| F-003 | HAL 硬件抽象层（ADC + GPIO 接口） | P0 |
| F-004 | Unity 单元测试框架集成 | P0 |
| F-005 | CMock 自动桩生成 | P0 |
| F-006 | Makefile + CMake 双构建 | P0 |
| F-007 | GitHub Actions CI/CD 流水线 | P0 |
| F-008 | 完整中文文档链（MRD→运维） | P1 |

### 6.2 后续迭代（非 MVP）

| 编号 | 需求 | 计划版本 |
|------|------|----------|
| F-101 | UART 通信模块 | v1.1 |
| F-102 | SPI Flash 存储模块 | v1.2 |
| F-103 | FreeRTOS 集成 | v1.3 |
| F-104 | 模块脚手架生成工具 | v2.0 |
| F-105 | 硬件在环测试（HIL） | v2.0 |

### 6.3 明确不做

- 不涉及具体芯片的寄存器级驱动（仅提供 HAL 接口）
- 不做 RTOS 内核移植
- 不做上位机软件
- 不做 PCB 设计

## 8. 风险与约束

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| CMock 版本升级导致 API 变化 | 桩生成失败 | vendor 固定版本，锁定 CMockConfig.yml |
| GitHub Actions runner 镜像更新 | CI 构建失败 | 使用 Ninja+MSVC 稳定方案，排错日志记录 |
| 用户 Ruby 环境缺失 | 无法重新生成桩 | 桩文件检入仓库，无 Ruby 可直接编译 |
| 跨平台路径差异 | Windows 编译失败 | Makefile 动态检测 OS，CMake 统一路径 |
