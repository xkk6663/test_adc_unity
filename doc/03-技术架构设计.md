## 1. 设计目标

1. **可测试性**：业务代码与硬件完全解耦，可在 PC 上单元测试
2. **可移植性**：更换 MCU 平台时只需重写 HAL 实现，业务代码零修改
3. **可维护性**：按职责分层，目录结构即架构，新人可快速定位
4. **可扩展性**：新增模块遵循固定模式，CI/CD 自动覆盖

## 2. 总体架构

### 2.1 分层架构图

```
┌─────────────────────────────────────────────────────────────┐
│                        应用层 (app/)                         │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐       │
│  │   battery    │  │     led      │  │  (未来模块)   │       │
│  │  电压采集     │  │  LED 指示     │  │              │       │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘       │
├─────────┼─────────────────┼─────────────────┼───────────────┤
│         │        硬件抽象层 (hal/)           │               │
│  ┌──────▼───────┐  ┌──────▼───────┐  ┌──────▼───────┐       │
│  │   hal_adc    │  │   hal_gpio   │  │  (未来接口)   │       │

│  ┌──────────────────────────────────────────────────────┐   │
│  │              firmware/  固件主程序                      │   │

│  └──────────────────────────────────────────────────────┘   │
├─────────────────────────────────────────────────────────────┤
│                       测试层 (test/)                         │
│  ┌──────────────────┐  ┌──────────────────────────────┐     │
│  │   unit/ 单元测试  │  │   mocks/ CMock 自动桩         │     │
│  │  test_battery.c  │  │  mock_hal_adc.c/h             │     │
│  │  test_led.c      │  │  mock_hal_gpio.c/h            │     │
│  │  test_support.c  │  │                              │     │
│  └──────────────────┘  └──────────────────────────────┘     │
├─────────────────────────────────────────────────────────────┤
│                    框架层 (framework/)                       │
│  ┌──────────────────┐  ┌──────────────────────────────┐     │
│  │   unity/         │  │   cmock/                     │     │
│  │  测试断言框架     │  │  桩生成器 + C 运行时           │     │
│  └──────────────────┘  └──────────────────────────────┘     │

│  │  桩生成入口       │  │  桩生成配置                   │     │
│  └──────────────────┘  └──────────────────────────────┘     │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 依赖方向

```
app/ ──→ hal/ ←── platform/
  │         ↑
  │         │
  └──→ test/ ──→ framework/
         │
         └──→ tools/
```

- **上层依赖下层**：app/ 依赖 hal/，test/ 依赖 app/ 和 hal/
- **下层不感知上层**：hal/ 不包含任何 app/ 的引用
- **横向不依赖**：app/battery/ 和 app/led/ 互不依赖

## 3. 各层详细设计

### 3.1 应用层（app/）

**职责**：实现业务逻辑，只面向 hal/ 接口编程，不直接操作硬件寄存器。

**模块划分**：

| 模块 | 目录 | 职责 | 公开接口 |
|------|------|------|----------|
| battery | app/battery/ | 电池电压采集与换算 | `adc_to_mv()`, `read_battery_mv()` |
| led | app/led/ | LED 状态机控制 | `led_set_by_voltage()`, `led_get_state()` |

**设计约束**：
- 每个模块一个目录，包含 `.c` 和 `.h`
- 头文件只暴露公开接口，内部变量/函数声明在 `.c` 中用 `static`
- 不允许 `#include` 其他模块的内部头文件
- 硬件参数（参考电压、ADC 分辨率）用宏定义在头文件中

### 3.2 硬件抽象层（hal/）

**职责**：定义硬件操作的统一接口，是业务代码与硬件之间的契约。

**接口定义**：

| 头文件 | 接口函数 | 说明 |
|--------|----------|------|
| hal_adc.h | `uint16_t HAL_ADC_GetValue(void)` | 读取 ADC 原始值（0~4095） |
| hal_gpio.h | `void HAL_GPIO_SetPin(uint8_t pin, uint8_t level)` | 设置 GPIO 引脚电平 |

**设计约束**：
- 只有 `.h` 文件，没有 `.c`（实现由平台层或测试桩提供）
- 函数名统一前缀 `HAL_`
- 参数和返回值使用 `stdint.h` 固定宽度类型
- 不包含任何平台相关头文件

### 3.3 平台层（platform/）

**职责**：固件主程序 + 真实 HAL 实现，编译为可在硬件或 PC 模拟器上运行的固件。

**当前实现**：`platform/firmware/firmware_main.c`
- 包含 `main()` 函数，模拟固件主循环
- 包含真实 HAL 的 PC 模拟实现（用随机数模拟 ADC，用打印模拟 GPIO）

**扩展方式**：
- 新增 `platform/stm32/` 目录，放置 STM32 的 HAL 实现和启动文件
- 新增 `platform/esp32/` 目录，放置 ESP-IDF 的适配层

### 3.4 测试层（test/）

#### 3.4.1 unit/ —— 单元测试用例

| 文件 | 测试对象 | 用例数 | 测试方法 |
|------|----------|--------|----------|
| test_battery.c | battery 模块 | 11 | 等价类+边界值+错误推测+接口交互 |
| test_led.c | led 模块 | 8 | 等价类+边界值+状态切换+接口交互 |
| test_support.c | 测试固件 | - | 统一 setUp/tearDown/main |

**test_support.c 的作用**：
- 统一管理所有 CMock 桩的初始化/校验/销毁
- 统一 `main()` 函数，通过 `RUN_TEST()` 注册所有用例
- 新增模块时只需在此添加 extern 声明和 RUN_TEST

#### 3.4.2 mocks/ —— CMock 自动桩

| 桩文件 | 对应接口 | 生成方式 |
|--------|----------|----------|
| mock_hal_adc.c/h | hal_adc.h | `ruby tools/gen_mocks.rb` |
| mock_hal_gpio.c/h | hal_gpio.h | `ruby tools/gen_mocks.rb` |

**桩的能力**（CMock 插件）：
- `:expect` —— 预设返回值和参数校验
- `:ignore` —— 忽略特定函数的调用

### 3.5 框架层（framework/）

**职责**：第三方测试框架，vendor 到工程，无需额外安装。

| 框架 | 目录 | 用途 | 关键文件 |
|------|------|------|----------|
| Unity | framework/unity/ | 测试断言 + 运行器 | unity.c/h, auto/type_sanitizer.rb |
| CMock | framework/cmock/ | 桩生成器 + C 运行时 | lib/*.rb, src/cmock.c/h |

**为什么 vendor 而不是用包管理器**：
- 嵌入式开发环境通常没有 gem/npm
- 锁定版本，避免上游更新导致不兼容
- 离线环境也能编译运行

### 3.6 工具层（tools/）

| 文件 | 用途 |
|------|------|
| gen_mocks.rb | CMock 桩生成入口，指定要生成桩的头文件列表 |
| CMockConfig.yml | CMock 配置（输出路径、插件、前缀等） |

## 4. 双目标编译设计

同一份业务代码（app/）被两个目标同时链接：

```
┌──────────────────┐          ┌──────────────────┐
│    unit_test     │          │  firmware_demo   │
│   (PC 测试目标)   │          │   (固件目标)      │
├──────────────────┤          ├──────────────────┤
│ test/unit/*.c    │          │ platform/        │
│ app/battery/*.c  │          │  firmware/       │
│ app/led/*.c      │          │  main.c          │
│ test/mocks/*.c   │          │  (真实 HAL)       │
│ framework/       │          │ app/battery/*.c  │
│  unity.c         │          │ app/led/*.c      │
│  cmock.c         │          │                  │
└──────────────────┘          └──────────────────┘
```

**关键设计**：
- `unit_test` 链接 `test/mocks/mock_hal_*.c`（CMock 桩替换真实 HAL）
- `firmware_demo` 链接 `platform/firmware/firmware_main.c`（真实 HAL 实现）
- 两个目标共享 `app/` 下的业务代码，确保测试的代码就是运行的代码

## 5. 构建系统设计

### 5.1 CMake（唯一构建系统）

```
cmake_minimum_required(VERSION 3.10)
project(unity_cmock_demo C)

# 统一头文件路径（按架构分层）
include_directories(app/battery app/led hal test/mocks
                    framework/unity framework/cmock/src)

# 编译警告
if(CMAKE_C_COMPILER_ID MATCHES "GNU|Clang")
    add_compile_options(-Wall -Wextra)
endif()

# 覆盖率支持（CI coverage Job 使用）
option(ENABLE_COVERAGE "Enable gcov coverage" OFF)
if(ENABLE_COVERAGE)
    add_compile_options(--coverage -O0 -g)
    add_link_options(--coverage)
endif()

# 单元测试目标
add_executable(unit_test ${TEST_SRCS})
enable_testing()
add_test(NAME unit_test COMMAND unit_test)

# 固件目标
add_executable(firmware_demo ${FW_SRCS})
```

**为什么只用 CMake？**
- 跨平台一致性：Windows/Linux/macOS 同一套构建配置
- CI 简化：不需要维护 Makefile 和 CMake 两套
- 覆盖率集成：通过 `ENABLE_COVERAGE` 选项一键开启
- 生态成熟：CMake 是 C/C++ 项目的事实标准

## 6. CI/CD 架构设计

### 6.1 三 Job 流水线

```
push/PR
   │
   ▼
┌──────────────────┐
│ static-analysis  │  cppcheck 检查 app/hal/platform
│  (Ubuntu)        │  发现 error 即失败
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  build-and-test  │  三平台矩阵
│  (矩阵)           │  Ubuntu/gcc  macOS/clang  Windows/MSVC(Ninja)
│                  │  每平台：桩生成 → 构建 → 测试 → 固件运行
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│    coverage      │  gcov 编译 → 运行测试 → lcov 生成报告
│  (Ubuntu)        │  排除 framework/test/tools，上传 HTML
└──────────────────┘
```

### 6.2 设计决策

| 决策 | 理由 |
|------|------|
| static-analysis 独立 Job | 快速反馈，代码风格问题不阻塞构建调试 |
| 多平台矩阵 | 确保跨平台可编译，提前发现平台特定问题 |
| Windows 用 Ninja+MSVC | Visual Studio 生成器在 runner 上不稳定（见排错日志 #07） |
| coverage 仅 Ubuntu | gcov/lcov 在 Linux 最成熟，其他平台覆盖率工具差异大 |
| fail-fast: false | 一个平台失败不影响其他平台，便于同时排查 |

## 7. 技术选型决策记录

| 技术 | 选型 | 备选 | 决策理由 |
|------|------|------|----------|
| 测试框架 | Unity | CUnit / Google Test | 轻量、纯 C、嵌入式社区标准 |
| 桩生成 | CMock | 手写桩 / FFF | 自动生成、与 Unity 配套、功能完整 |
| 构建系统 | CMake | Makefile | 跨平台一致，CI 简化，覆盖率集成方便 |
| CI 平台 | GitHub Actions | GitLab CI / Jenkins | 与仓库集成、免费额度充足 |
| 静态分析 | cppcheck | clang-tidy / PC-lint | 开源、跨平台、CI 易集成 |
| 覆盖率 | gcov + lcov | gcovr / OpenCppCoverage | Linux 上最成熟、HTML 报告美观 |
| 架构参考 | ELAB 框架 | 自研分层 | 成熟的嵌入式分层实践 |
